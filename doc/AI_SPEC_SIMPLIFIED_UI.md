# AI spec: simplified KOReader interface

Status: research and implementation brief, 2026-10-07. Repo examined at `22ea2320c`.

## Goal

Build a simple book browser and reading interface that keeps KOReader's document loading, rendering, pagination, persistence, and device support. Replace the everyday settings and tap menus with a small, consistent set of controls. Keep KOReader source files unchanged if the result remains maintainable.

## Decision

**A separate browser and its top-level menu can be built as a Lua plugin without replacing KOReader methods. The reader's normal top-menu tap can also open a plugin-owned menu without method replacement.** The hard part is a guarantee that *every* stock entry point and reader-specific popup has been replaced. Those surfaces have different owners and may require per-surface integration, runtime overrides, or new frontend hooks. The native document engines do not need changes for this UI project.

The key design choice is whether to **replace the existing FileManager and Menu implementations** or **show a separate plugin-owned full-screen browser and menu**. The latter can sit above FileManager and consume its own input. It can call the same reader, settings, action, and event interfaces used elsewhere in KOReader. It still needs careful startup/return lifecycle work, and some menu callbacks are coupled to KOReader's stock `TouchMenu` instance. KOReader's Cover Browser and Project: Title chose the first route for their browser presentation; they replace FileChooser/FileManager/Menu methods and pay a compatibility cost. See [Cover Browser](../plugins/coverbrowser.koplugin/main.lua), [Project: Title source](https://github.com/joshuacant/ProjectTitle/blob/master/main.lua), and [Project: Title compatibility policy](https://github.com/joshuacant/ProjectTitle/wiki/Use-With-Nightly-KOReader-Builds).

## Relevant architecture

- `reader.lua` chooses a startup destination: a document, FileManager, history, favorites, or shortcuts. The normal browser is `FileManager:showFiles`; document opening goes through `ReaderUI:showReader` and `DocumentRegistry:openDocument`. See [startup](../reader.lua), [FileManager](../frontend/apps/filemanager/filemanager.lua), [ReaderUI](../frontend/apps/reader/readerui.lua), and [DocumentRegistry](../frontend/document/documentregistry.lua).
- FileManager builds its title bar and FileChooser in `setupLayout`. ReaderUI creates a ReaderView, input and feature modules, then loads plugins. FileManager loads plugins before `setupLayout` and invokes registered post-init callbacks before `showFiles` shows FileManager. A plugin can schedule its own full-screen browser to be shown above FileManager after that step; it should close its browser before opening a book and show a fresh one when FileManager is recreated on return. See [FileManager setup](../frontend/apps/filemanager/filemanager.lua), [ReaderUI setup](../frontend/apps/reader/readerui.lua), and [UIManager window stack](../frontend/ui/uimanager.lua).
- The rendering layer is behind document providers: e.g. EPUB and other reflowable formats use `credocument`; PDF uses `pdfdocument`/MuPDF. ReaderUI owns the document and reader view. A UI plugin should call KOReader's open and navigation APIs instead of building a second rendering stack. See [credocument](../frontend/document/credocument.lua), [pdfdocument](../frontend/document/pdfdocument.lua), and [ReaderView](../frontend/apps/reader/modules/readerview.lua).
- Plugins are directories ending in `.koplugin` with `main.lua` and metadata in `_meta.lua`. They are loaded from `plugins` and configured extra paths, then instantiated separately inside FileManager and ReaderUI; document-only plugins are skipped in FileManager. A plugin can receive `ui`, `view`, and `document`, register event handlers, add menu items, and show widgets through UIManager. See [PluginLoader](../frontend/pluginloader.lua), [hello example](../plugins/hello.koplugin/main.lua), and [UIManager API](https://koreader.rocks/doc/modules/ui.uimanager.html).
- There is no single global menu model. The reader top menu, file browser top menu, reader bottom configuration panel, text highlight dialog, link dialog, dictionary popup, and file hold dialog have different owners. See [ReaderMenu](../frontend/apps/reader/modules/readermenu.lua), [FileManagerMenu](../frontend/apps/filemanager/filemanagermenu.lua), [ReaderConfig](../frontend/apps/reader/modules/readerconfig.lua), [ReaderHighlight](../frontend/apps/reader/modules/readerhighlight.lua), [ReaderLink](../frontend/apps/reader/modules/readerlink.lua), and [FileManager file dialog](../frontend/apps/filemanager/filemanager.lua).

## Three distinct UI surfaces

1. **Main browser and its top menu:** Build both as plugin-owned full-screen widgets. A top widget receives input before the FileManager window below it; when it consumes taps, the stock browser/menu does not see them. This does not require changing FileChooser, FileManager, or Menu methods. Launch and return need a deferred show after FileManager exists. The underlying FileManager can continue to own book-open and document-provider behavior.
2. **Reader's ordinary top menu:** ReaderMenu's tap, swipe, and pan zones are registered on the ReaderUI input container. `registerTouchZones` explicitly allows same-ID replacement, and `unRegisterTouchZones` can remove zones. A plugin can take these zones after `ReaderReady` and after dimension changes, then show its own menu. That avoids overriding `ReaderMenu:onShowMenu` for the normal touch path. The stock Menu key, Dispatcher `ShowMenu` action, menu search/rebuild events, and other direct invocations remain separate entry points to audit if the goal is total replacement.
3. **Menus and dialogs within reader view:** The bottom `ReaderConfig` panel has its own zones and key route. Text selection, link, dictionary, and some file/book dialogs come from other modules. A plugin can register or remove touch zones for the bottom panel and build its own simple controls, while existing button-extension APIs can add actions to some popups. A uniform replacement of *all* those contextual surfaces has no single hook; each must be handled or retained as an explicit stock fallback.

The `UIManager:sendEvent` window stack, `InputContainer:registerTouchZones`, [ReaderMenu zones](../frontend/apps/reader/modules/readermenu.lua), and [ReaderConfig zones](../frontend/apps/reader/modules/readerconfig.lua) establish the touch-routing behavior. This is still integration with KOReader internals: zone IDs, event order, and startup lifecycle should be tested across target versions. It is **not** method monkey patching.

## Capability matrix

“Plugin API” below means an existing extension point or a plugin-owned widget. “Override” means Lua monkey patching of an internal class or instance method from a plugin or user patch; it leaves installed source files alone but ties the plugin to internals.

| Desired change | Plugin API / configuration | Runtime override without source edit | Core frontend work for a durable solution |
| --- | --- | --- | --- |
| New main book browser screen with custom layout and simple navigation | Yes: show a plugin-owned full-screen widget above FileManager; handle its own taps; open a book through FileManager/ReaderUI; re-show on return | Only if modifying FileManager's own screen or replacing its lifecycle | A startup/home screen factory would make the handoff cleaner, but is not a prerequisite for the separate-screen approach |
| Change cover/list presentation inside stock browser | No dedicated skin/theme API | Yes: Cover Browser and Project: Title replace FileChooser/FileManager methods | Add browser row, grid, title bar, and context action providers rather than copying methods |
| Add settings or actions to reader/file browser top menus | Yes: `registerToMainMenu` / `addToMainMenu`; menu items support callbacks and sorting hints | No | No |
| Reorder and hide stock **top-menu** entries | Yes: user `reader_menu_order.lua` / `filemanager_menu_order.lua` read by MenuSorter; `KOMenu:disabled` handles unused entries | No | No, if the underlying top menu layout is acceptable |
| Show a custom top-level menu from the plugin browser | Yes: browser-owned widget and tap handler; wire selected controls to existing events, Dispatcher actions, settings, and module methods | No | No |
| Show a custom menu from the reader's normal top-menu tap | Yes: register replacement ReaderUI touch zones after core zones are installed, then show a plugin widget | Only if direct stock menu invocations must also be intercepted | Add a reader menu presenter hook for a guaranteed replacement across tap, key, Dispatcher, and rebuild paths |
| Redirect the normal bottom-panel touch gesture to simple settings | Yes: replace/remove ReaderConfig touch zones and show a plugin widget | Only if all key/direct `ShowConfigMenu` paths and stock dialog behavior must be replaced | Add an explicit panel presenter/disable hook for a guaranteed replacement |
| Add actions to text selection, external-link, and dictionary popups | Yes, for these specific surfaces: highlight and link button registration; dictionary button specs | No | No |
| Replace all text selection, link, dictionary, and file hold dialogs with one new design | No single context-menu replacement API | Yes, separately for each owning module and some instance methods | Add per-surface dialog factories/action providers or a common context-action model |
| Redirect tap/swipe zones and keyboard shortcuts | Touch zones support registration/removal; plugin must reapply after reader readiness and resizing. Keys and Dispatcher calls require separate mapping or handling | Possibly for remaining direct stock entry points | Add explicit disable/replace controls if a universal route is required |
| Change document rendering/pagination implementation | Plugins can call exposed document/reader methods and configure options | Lua overrides can alter integration behavior; not a substitute for native engine development | Change engine/backend only for new rendering behavior, not for the UI requested here |

Evidence for the menu claims: [MenuSorter](../frontend/ui/menusorter.lua) reads per-user order files; [ReaderMenu](../frontend/apps/reader/modules/readermenu.lua) and [FileManagerMenu](../frontend/apps/filemanager/filemanagermenu.lua) create `TouchMenu`/`Menu` directly when *their* show methods run; [ReaderConfig](../frontend/apps/reader/modules/readerconfig.lua) creates `ConfigDialog` directly. A plugin-owned menu need not call those show methods. [ReaderHighlight](../frontend/apps/reader/modules/readerhighlight.lua), [ReaderLink](../frontend/apps/reader/modules/readerlink.lua), and [ReaderDictionary](../frontend/apps/reader/modules/readerdictionary.lua) expose narrower button registration APIs. `InputContainer:registerTouchZones` supports same-ID replacement; it does not redirect keys or direct events. See [InputContainer](../frontend/ui/widget/container/inputcontainer.lua).

## Recommended implementation shape

### Phase 1: plugin-owned browser and top menus

Create `plugins/simpleui.koplugin` (or distribute it externally) with `main.lua`, `_meta.lua`, and plugin-owned browser, top menu, and settings widgets. No core method replacement is required for the browser or the normal touch-driven top menus.

1. Build a separate full-screen browse widget with a small home view, folders/collections or recent books, covers/title/author, search, and a simple book action. From FileManager plugin init, schedule its display after FileManager is on the UIManager stack; close it before opening a book. Reuse KOReader metadata and document-provider checks. Open selected books through `FileManager:openFile` or `ReaderUI:showReader`; do not call engine internals directly. On ReaderUI's normal Home path, FileManager is created again, so the plugin can show the browser again.
2. Put the browser's top-level menu inside the plugin widget. Its tap handler shows the plugin's settings/actions UI and consumes the gesture, so the underlying FileManager does not receive it. Keep a deliberate **Advanced KOReader settings** route.
3. In ReaderUI, register the plugin's top-menu tap/swipe/pan zones after ReaderMenu registers its zones at `ReaderReady`; reapply after rotation/resizing. Those handlers show the same simple menu adapted to the open book. The plugin can likewise take the bottom-panel touch zones if its simple settings cover that path.
4. Implement each menu action against a suitable KOReader interface: `Dispatcher` for registered actions, `Event`/reader modules for reader controls, settings objects for stored preferences, and existing widgets for dedicated dialogs. For example, `Dispatcher` exposes Home, font-size, and frontlight actions. Do **not** assume every stock menu callback is a reusable API: some closures expect a `touchmenu_instance`, call `updateItems`, or manipulate stock menu state. Use the underlying action or write a small adapter for the chosen feature.
5. Confirm behavior on both reflowable and paged documents. The two families use different reader controllers and bottom panel options. Audit direct Menu-key and Dispatcher menu actions separately from tap zones.

This phase can deliver the intended main browser and top-level touch menu without monkey patching. Stock contextual popups, direct menu actions, and system flows may still be reachable; their presence should be listed explicitly.

### Phase 2: reader-specific menus and comprehensive routing

Decide which reader-specific dialogs should be kept, simplified, or wholly replaced: bottom configuration, text selection/highlight, link, dictionary, search, table of contents, and book/file hold actions. For each, identify its owning module, touch and key routes, and usable button/action APIs. Register custom zones or use existing button hooks where sufficient. Keep stock versions behind Advanced settings for infrequent operations if that meets the product goal.

If the requirement is stronger—*no stock reader menu can appear from any tap, key, Dispatcher action, or internal call*—choose one of two paths for the remaining surfaces:

**External plugin with internal overrides.** Intercept only the remaining direct entry points and context-dialog owners. Prefer narrow instance wrappers; avoid globally replacing `Menu`/`FileChooser` because they are reused in unrelated pickers. Keep original methods for fallback and pin each release to a tested KOReader version. This leaves core files untouched but requires compatibility work.

**Small KOReader frontend changes plus plugin.** Add explicit presenters/factories and opt-out controls for the bottom panel and selected context dialogs, plus a single route for top-menu taps, keys, and Dispatcher calls. The simplified widgets remain in the plugin. A startup/home screen factory could avoid the deferred full-screen browser overlay. This is the durable route if universal replacement and routine upstream updates are both requirements. It changes Lua frontend source, not the document engines.

Do not replace the whole `UIManager` or ReaderUI just to change menus: those also manage repaint, input, lifecycle, persistence, and provider integration. A new outer application using KOReader's engine alone would require extracting and recreating that integration; it is a substantially larger project than a frontend plugin.

## Acceptance criteria for a future implementation

- On launch and on return from a book, normal library navigation shows the plugin browser; opening a supported book still uses KOReader's reader and preserves progress and sidecar settings. No stock FileManager tap leaks through the full-screen browser.
- A normal menu tap in the browser and in a document shows the plugin menu. Bottom edge gesture, book hold, text selection, external link, and dictionary lookup follow the specified simple UI behavior or an explicitly documented KOReader fallback. Keyboard and non-touch devices have an equivalent route if they are target platforms.
- Every core capability deliberately hidden from the everyday UI remains reachable through an Advanced settings path; critical device actions such as exit and brightness are reachable.
- EPUB and PDF/DjVu paths, screen rotation/resizing, e-ink refresh, return-to-library, restart, and plugin disable/recovery are checked on the intended devices.
- For any override-based portion, incompatible KOReader versions fail closed to stock UI rather than entering a crash loop; the exact supported version is documented. [Project: Title's own warning](https://github.com/joshuacant/ProjectTitle/wiki/Use-With-Nightly-KOReader-Builds) is a concrete precedent.

## Practical limits and source references

- KOReader's [developer docs](https://koreader.rocks/doc/) describe modules and widgets, but the strongest evidence for these boundaries is the event routing and construction code above. There is no declared whole-application skin/plugin interface in the inspected paths. A plugin-owned browser and menu do not need one; this is a repo-based finding, not a proof that no other third-party approach exists.
- [KOReader user patches](https://github.com/koreader/koreader/wiki/User-patches) and [userpatch.lua](../frontend/userpatch.lua) explicitly support runtime method replacement. That is another route to no source-file edits, with the same internal API risk. Android F-Droid builds disable user patches; ordinary plugins are a separate mechanism.
- [KOReader issue #13942](https://github.com/koreader/koreader/issues/13942) records the lack of stable deep UI extension points and the maintenance cost reported by Project: Title's developers. The issue is closed and labelled out of scope; plan for a private fork or independently maintained plugin rather than assuming upstream will add these hooks.
- [Project: Title](https://github.com/joshuacant/ProjectTitle) is a model for how far a plugin can go, but it targets the book browser, not a universal replacement of all reading settings and contextual menus.
